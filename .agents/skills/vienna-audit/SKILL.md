# Mihon Vienna 项目体检与大扫除流程

Mihon Vienna 是上游 `mihonapp/mihon` 的个人分支。任何体检与清理都必须遵守一个底线：**只聚焦 Vienna 自己新增和改动过的代码与配置，不无故重构未改动的上游文件**，避免将来合并上游时制造无谓冲突。

## 体检模式（默认只查不改，出报告让用户挑项）

除非用户明确要求“直接清理/修复”，否则先产出清晰的中文体检报告，让用户确认优先级后再按独立分支 + PR 逐步实施。

### 维度 1：静态扫描与客观指标
并行运行以下检查（按需跳过耗时过长的项并在报告里注明）：
1. **Detekt 静态分析**：`./gradlew detekt`
   - 核查是否出现新的复杂度超标、空 catch、吞异常、死代码或协程隐患。
   - 若需要查看当前基线里积压最严重的模块，可统计 `config/detekt/baseline.xml` 中各模块/文件的条数分布。
2. **超大文件与改动热点**：
   - 对比分叉根提交 `45d428d89..HEAD`，列出 Vienna 改动过、行数超过 1,000 行的 `.kt` 文件，检查是否出现职责混杂或可拆分的纯逻辑。
3. **Android Lint（按需定期跑）**：`./gradlew :app:lintDebug`
   - 重点过滤出 Vienna 改动文件相关的**未使用资源、生命周期/内存泄漏警告、缺失翻译或无障碍提示**。

### 维度 2：代码臃肿、重复与逻辑矛盾审查
重点抽查 Vienna 改动最密集的核心链路（`source-local/`、`ui/reader/`、`ui/audio/`、`ui/browse/source/browse/`、`ui/manga/`、`data/`、`domain/`）：
- **第二份事实来源**：同一份状态（计数、过滤条件、本地索引、播放状态、阅读进度）是否在多处各自缓存且同步口径不一致？
- **半成品读写链**：是否有只写入不读取的配置项、废弃偏好项、遗留兼容分支或不再触发的恢复路径？
- **重复逻辑**：同一套计算、筛选或转换是否在列表页、搜索页、统计页、详情页各写了一遍？
- **事务与异常安全**：本地文件移动/删除/合并与数据库写入是否成对事务化或可补偿；SAF 空目录返回是否会误清空已有索引？

### 维度 3：UI / 交互 / 文案一致性巡检
对照仓库根目录 `AGENTS.md` 中的「交互偏好」检查 Vienna 自定义或改动过的页面：
- **不统一**：同一个动作在不同页面是否换了图标、位置或叫法？
- **不简洁**：标题、标签、数值已经说清楚的地方，是否多了多余的副标题、脚注、说明段落或日常成功 Toast？
- **易误触 / 歧义**：会删数据或容易搞错范围的操作（如清空历史 vs 清空进度）是否清晰区分对象和后果？重要操作是否藏得太深（仅靠长按/颜色）？
- **多语言同步**：`i18n` 中 `base`、`zh-rCN`、`zh-rTW` 的新增文案是否齐全且口径一致？

### 维度 4：工作区与仓库卫生
检查但不擅自删除（除非用户明确授权）：
- 仓库根目录是否有残留临时文件/日志/导出（应统一放 `_tmp/` 且任务结束删除，切勿触碰仓库外 `D:\DATA\keys`）。
- 是否有已通过 PR 合并到 `main` 但仍堆积在本地的旧分支。
- `docs/` 中是否有明显过时或与现有代码矛盾的文档。

## 报告输出格式（面向非专业背景用户，说人话）

按下面 4 级输出，每条写清「在哪（可点击文件链接）+ 现状问题 + 用户能感受到的影响 + 建议动作 + 改动风险（低/中/高）」：
1. **高优先级：逻辑矛盾 / 隐患**（可能导致丢数据、计数不准、崩溃或功能打架）
2. **中优先级：明显臃肿 / 重复代码**（后续越改越容易出 Bug 的地方）
3. **体验优化：UI / 文案 / 交互不统一**（不够简洁美观或口径冲突的地方）
4. **卫生整理：废文件 / 旧分支 / 配置积灰**（零功能风险，随时可清）

最后给出推荐的 1–2 个最小切入点，由用户决定先修哪一项。
