# 备份与恢复完整性核查

核查日期：2026-11-17。核查基线：`origin/main` 的 `52abfe139`；交付前同步至 `551992801`。核查规模：500 部作品、3,000 个篇目。

本次只增加核查测试和本文档，不修改备份、恢复或阅读器行为，不操作手机主库，不安装 APK。

## 结论与边界

当前格式具备保存篇目进度、已读、书签、译名、手动排序、历史和标记所需的字段；恢复路径会按作品与篇目地址重新关联数据库 ID。本次隔离测试覆盖这些字段的编码、部分创建与恢复逻辑，以及 SQL 写入和事务回滚。它不等于在真实手机上完成了一次清空环境后的完整恢复。

已确认两处缺口：旧备份缺少手动排序字段时，恢复到已有数据可能把排序写成 0；自定义篇目封面恢复失败可能没有出现在恢复错误报告里。另外，“好本子”标记存在冷启动初始化窗口，尚未用并发测试或真机复现。

`.tachibk` 不包含漫画原文件、下载文件或整部作品的自定义主封面图片。搬家时仍需保存本地漫画目录。不能用“同一台手机恢复后封面还在”证明封面图片包含在备份中。

## 数据范围

| 数据 | 当前路径与核查结果 | 限制 |
| --- | --- | --- |
| 阅读进度、已读、书签、总页数 | 篇目字段有编码；恢复到已有篇目会保留已读、书签和有效的更远进度 | 需要开启篇目备份；恢复按地址匹配 |
| 篇目译名 | 保存 `translatedName`；当前格式编码往返与恢复参数有测试 | 旧备份缺字段时传入 null，SQL 保留已有译名 |
| 手动篇目排序 | 保存 `customOrder`；当前格式可恢复明确的排序值 | 旧备份缺字段时默认 0，存在覆盖缺口，见下文 |
| 阅读历史 | 保存篇目地址、时间和累计时长；恢复映射到目标 ID | 合并使用较新时间和较大累计时长，只补时长差值；需要开启历史备份 |
| 分类 | 保存分类及作品分类关系；恢复映射到目标分类 ID | 分类创建顺序已有测试，仍需独立环境验收界面显示 |
| 标记、“好本子” | 专用数据通过来源、作品地址、篇目地址重新关联 | 冷启动“好本子”快照有静态风险；不能仅凭标记条目存在就保证对应作品已被选入备份 |
| 本地篇目自定义封面 | 保存图片字节，恢复后按篇目地址映射到新 ID | 只导出有效且不超过 10 MiB 的图片；失败报告存在缺口 |
| 本地作品的自定义主封面 | 位于作品目录的 `cover.*`，不包含在备份图片字段内 | 需连同作品目录另行复制 |
| 在线作品的自定义主封面 | 位于应用封面缓存，按数据库 ID 存储 | `.tachibk` 不包含这份图片；换机时不能只依靠此备份保留 |
| 应用与来源设置 | 使用独立设置备份；专门恢复的标记键、可重建缓存和应用运行状态被排除 | 私密设置默认不选；不能把默认备份理解为所有登录信息也已保存 |
| 漫画原文件、压缩包、下载 | 不由元数据备份打包 | 需要单独文件备份 |

默认选项包含篇目、历史、分类和应用设置，私密设置默认关闭。取消“篇目”会同时排除篇目进度、书签、译名、排序和篇目封面。

本地作品从确认过的文件系统目录集合映射到数据库条目；来源不可用时备份会失败，不会把无法访问当成空库正常导出。尚未建立数据库行的文件没有数据库进度可导出。原目录或篇目地址改变后，恢复不能自动猜测任意新路径对应哪一个旧条目。

## 已复现：旧备份覆盖已有手动排序

已有篇目手动排序为 17；恢复不包含 Vienna 排序字段的旧格式篇目后，排序变成 0。原因是 `BackupChapter.customOrder` 的缺省值为 0，恢复没有区分“备份里没有这个字段”和“用户明确设置为 0”。

同一路径会把缺失的篇目 `memo` 变成空对象并写回，覆盖已有元数据，例如扫描得到的页数元数据。本次没有证据表明它会删除用户笔记；不要扩大结论。已有译名传入 null 时由 SQL 保留，有效进度和总页数另有保护。

证据：`BackupIntegrityAuditTest` 调用实际 `MangaRestorer`，观察到绑定的排序为 0、memo 为空对象；`verify_backup_integrity.py` 用仓库 SQL 在内存 SQLite 中确认覆盖结果。

后续修复应保留字段是否存在的信息，区别旧格式缺失与当前格式主动重置。不能简单把所有排序 0 都当成“不恢复”。本次不修改兼容策略。

## 已复现：篇目封面失败没有进入恢复错误报告

`LocalChapterCoverManager.restoreCustom()` 对空图片、超限图片、无法解码或无法写入返回 false。`MangaRestorer` 没有检查返回值；部分抛出的图片异常也只写日志，未传到恢复汇总。

隔离测试让图片恢复返回 false，确认数据库事务已经提交且漫画恢复正常返回。因此可能出现进度恢复了、选定的篇目封面缺失，但恢复结果没有列出该错误的情况。这不代表整部作品的数据库恢复失败。

后续应在保留已恢复数据的同时汇总具体图片失败，避免用户误以为所有图片已恢复。当前导出也会跳过无效或超过 10 MiB 的篇目封面，应一并评估如何报告。

## 静态风险：冷启动备份可能过早读取“好本子”

`GoodDoujinStore` 初始状态为空列表，通过后台协程迁移旧数据并订阅数据库后才填入标记。它在依赖容器中按需创建。`BackupCreator.backupMarks()` 取得该实例后立即读取 `marks.value`，没有等待首次读取完成。

如果应用刚启动、尚未使用过该标记存储，此时后台备份有机会读取初始空列表。旧的标记设置键又被专门恢复策略排除，不能作为第二份兜底。

这是初始化与读取顺序形成的代码风险，本次未确定实际设备触发频率，也未用确定性的并发测试复现。下一批应先补受控初始化测试，再决定直接读数据库快照或等待初始化；不应靠随意延时解决。

## 自动验证与实际覆盖

新增 `BackupIntegrityAuditTest` 共 9 项：

1. 500 部作品、3,000 篇目的当前流式格式往返，保留全部编码字段及 1,000 条标记元数据，不沿用旧数据库数字 ID。此处图片为模拟字节，不验证 Android 图片解码。
2. 实际篇目查询 mapper、备份创建器和编码链保留篇目扩展字段与本地封面字节。
3. 不备份篇目时，相应用户字段和图片也不会导出。
4. 新恢复的作品、篇目、历史、分类和封面使用目标 ID，图片恢复发生在数据库提交之后。
5. 已有篇目保留稳定 ID、有效的更远进度和书签；明确的备份排序正常应用。
6. 观察旧备份默认值覆盖现有排序的缺口。
7. 观察封面返回 false 后仍正常返回的缺口。
8. 历史合并取较新日期，300 与 500 的累计时长只补 200。
9. 注入数据库更新异常时触发外层事务回滚，不开始封面恢复。

其中数据库驱动是记录实际生成 SQL 参数和事务调用的受控实现，不执行磁盘数据库。第 6、7 项用于固定缺口的复现证据；测试通过不代表缺口已修复，修复时须更新相应断言。

新增 `scripts/verify_backup_integrity.py` 共 5 项，执行仓库 SQL 和内存 SQLite：旧值覆盖、当前字段写入、历史时长幂等、标记目标归属、后续外键错误时章节与标记整体回滚。该脚本复用现有建表工具，没有加载生产数据库的全部触发器，因此不声称覆盖所有触发器效果。CI 加入该脚本。

既有测试另覆盖备份流格式兼容、损坏文件预检、取消、恢复先后顺序、历史字段修正及设置键排除。源码检查覆盖共享创建器、恢复器、两类标记存储和两类封面路径。

验证命令：

```text
./gradlew spotlessCheck testDebugUnitTest verifySqlDelightMigration
./gradlew :app:compileViennaKotlin
python -B scripts/verify_backup_integrity.py
```

上述三组检查均通过，新增 9 项 Kotlin 测试和 5 项 SQLite 检查均通过。

本次未做设备文件复制与独立环境完整恢复，没有测量实际 500 部作品的备份耗时、峰值内存和图片解码。编码规模测试不能替代这些测量。

## 可选手动验收

本次没有界面行为变化，不需要安装新包。无需在主库恢复旧备份来重复上述故障测试。

1. 在“更多 → 设置 → 数据与存储 → 备份与还原”创建一份备份，保留作品、篇目、历史、分类与应用设置等默认项目。预期导出一个 `.tachibk` 文件，且无创建失败提示。
2. 把该文件复制到电脑或另一份独立存储；另行复制需要保留的漫画目录及其中的 `cover.*`。预期两份备份都可读取，原目录保持不变。
3. 只有准备了独立测试设备或隔离环境时，才在那里恢复：使用少量测试漫画副本，在相同逻辑目录位置放好文件，再选择这份备份。无需清除主应用数据或改主库路径。
4. 在测试环境对照同一篇目的续读位置、已读、书签、译名、排序、标记、历史与篇目自定义封面，并从详情页进入阅读器后退出再进入。预期用户状态对应原篇目，且退出后能够续读。
5. 在测试环境重复恢复同一份备份，检查历史累计时长未翻倍、已有较远进度未倒退。没有隔离环境时跳过恢复操作，保留备份文件即可。

状态关联到错误篇目、译名或书签丢失、进度倒退、历史翻倍，均属于需要调查的回归。主封面未随元数据备份出现属于当前已知范围限制；篇目封面缺失却无错误报告则对应已确认的报告缺口。手机端验收仍由用户操作，agent 负责日志。
